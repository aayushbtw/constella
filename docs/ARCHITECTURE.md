# Architecture

## Stack

- **Base UI underneath.** Behavior, focus and accessibility come from the primitive. A component adds styling and composition, never its own version of what Base UI already handles. [UI SDK](#ui-sdk-watch) is the planned replacement, once it's ready.
- **StyleX only.** Most shadcn registries ship Tailwind, so another one adds nothing.
- **Command is Base UI too.** shadcn's Command is cmdk; ours is Base UI's Autocomplete, inline and always open, so it filters the `items` it's given rather than its children.
- **TanStack for data.** A data table renders a `useTable` instance the app builds with its own features (Table v9), virtualizes with TanStack Virtual against the window or a `scrollRef`, and reads its loading, stale and error states from a TanStack Query `useQuery` result; the app owns state, the component owns markup. A chart renders a TanStack Charts definition the app builds; the definition owns marks, scales, focus and the tooltip's behavior, the component owns the surface, the tooltip's markup and the legend. The palette reaches the library through the `--ts-chart-*` names it reads, set in `base.css`, so a definition needs no theme. Markdown renders TanStack Markdown with Constella's parts mapped onto its tags, its fences in a Code Block; the app passes the highlighter and adds its theme CSS, since the language set and code colors are its choice. Code Block ships no highlighter for the same reason. The app renders its tokens inside each `CodeBlockLine`. Docs list these under their own TanStack sidebar section.
- **Motion is StyleX and CSS.** No animation library: transitions, keyframes and Base UI's data attributes (`data-starting-style`, `data-ending-style`) cover it, and consumers install nothing extra.
- **Except a chart's data.** SVG geometry has no CSS transition, so `useChartTween` eases the values and the chart redraws each frame, timed by a Web Animation so it keeps the `out` curve and DevTools' playback speed. TanStack's own `svgAnimation` and `motion()` morph shapes instead: arcs bend across the ring and the axis disagrees with the marks mid-change, so neither is used.

## Workspace

`packages/ui` is the registry and holds only what ships; `apps/site` is the docs site and never ships. The library imports with `@/` because the shadcn CLI only rewrites `@/lib/*` and `@/components/*` to the consumer's aliases. The site maps `@/` to the library, as a consumer would, and uses `~/` for its own code. `shadcn build` writes the registry into the site's `public/r`. `packages/lint` is `@constella/lint`, an oxlint plugin for the rules below that a type check can't catch; the root config loads it like a consumer would.

**Site routes.** `__root.tsx` is the HTML shell only. Pages live under the pathless `_site` layout, which adds the Header and Toaster (`SiteChrome`, also wrapped around the root's not-found page). Dev-only capture pages for social posts (`/poster`, `/clip`) live under `_dev`, which has no chrome and 404s in builds through `devOnly`. A dev page that needs the chrome, like `/break`, stays in `_site` and calls `devOnly` itself. The Markdown and `llms.txt` server routes sit in the `(text)` group, which changes no URL.

## Registry

Every `registry:lib` file lives in `src/lib/constella/`, so an install keeps it apart from the app's own `lib` files. `base` is the floor every component depends on: the tokens, plus `base.css` with the Radix scales, theme and focus ring, `motion.ts` for behavior two popups share, and `styles.ts` with the styles parts share: `joinStyles`, the ButtonGroup corners and edges every joinable part applies after its own styles, `typeStyles`, the type scale's steps (size and line height together) a part puts before its own styles, `textWeights` and `textColors`, the weights and colors those three take as props, as lists with their styles in `textWeightStyles` and `textColorStyles`, and `visuallyHidden`, for text only screen readers get. The app `@import`s `base.css` from the stylesheet its root links; CSS a module imports applies after the first layout in dev, so the preflight's margins would shift the page. Parts take `typeStyles` rather than Text, Heading and Caption, since a part already renders its own element and its size often follows a selector; app code and the site's demos use `Text`, `Heading` and `Caption`. `Link` and `Code` are different: they style an inline element rather than set a step, so parts compose them as they do Table (Markdown renders its links and inline code with them). `base.css` imports `reset.css`, a preflight after Tailwind's: border-box sizing and no default margins, block media, controls and links that take the page's font and color, a bare button, `optimizeLegibility` text, balanced headings and pretty paragraphs, and `[hidden]` that no `display` overrides. Unlike Tailwind's, it keeps lists' padding and markers and headings' sizes, since Markdown and Field draw with the browser's; an app that renders bare lists or headings resets those itself, as the site does. StyleX can't evaluate an imported helper inside `stylex.create`, but a created style passes across files like any value. Shared foundations stay in `base` even if a component skips some of them; colors are small. A component gets its own item only for something specific to it and heavy.

**Components and blocks.** A component (`registry:ui`) is a part an app assembles, including AI parts built on other components (Citation is a Badge and a Hover Card). Its files live in `src/components/<group>/` and import as `@/components/primitives/alert`, grouped like Interfere's. The group is its docs section (`primitives`, `typography`, `ai`, `tanstack`), and the page lint fails when they disagree. Its files are typed `registry:component`, not `registry:ui`: `shadcn add` flattens a `registry:ui` file outside `components/ui` into the app's `ui` folder and leaves its imports dangling, while a `registry:component` file keeps its group under the app's `components` alias. A block (`registry:block`, its files `registry:component` in `src/components/`, so they install where an app keeps its own) is a whole section: a page, a form, a chat screen, copied in to edit. Blocks are exempt from the part rules below and are documented at `/blocks`.

**For agents.** Every item's `docs` names its page's Markdown URL, which `shadcn add` prints; a draft's item gets one when its page leaves draft, since drafts aren't built. After `shadcn build`, the site's build runs `scripts/registry-examples.ts`, which adds a `registry:example` `<name>-demo` per component page to `public/r`, so shadcn's MCP server returns usage snippets; they're labelled as snippets, since they don't compile alone. The agent skill is `skills/constella/`, installed from the repo with `npx skills add`: `SKILL.md` holds the rules that always apply and links `rules/*.md` (incorrect/correct pairs per topic) and `setup.md`, after shadcn's own skill. A rule that drifts goes there and in `@constella/lint`, not in one only. We'll build our own MCP server only if shadcn's turns out too limiting.

**Markdown.** The worker entry is `src/server.ts`: with `runWorkerFirst`, every page request passes through it, and `Accept: text/markdown` gets the page's `/index.md` route instead of HTML, with `Vary: Accept`; a miss is a Markdown 404 that links `llms.txt`. Markdown is served at request time, not prerendered. `/docs/installation/index.md`, `/docs/components/index.md` and `/blocks/index.md` have their own routes, since the `$slug` page routes would take `index.md` as a slug.

`registryDependencies` reference this registry by URL. A bare name like `base` means shadcn's official registry.

`vpr check` runs `packages/ui/scripts/check-registry.ts`: an item's direct imports must equal its `dependencies` (React aside, which the app provides) and its `registryDependencies`, even ones another dependency already brings, and every file in `src` belongs to exactly one item. `devDependencies` aren't checked.

## Composition

Components compose like shadcn: one file per component, made of small parts the consumer assembles. Data Table is the exception. Past 1,000 lines, it splits into parts (`data-table-action-bar`, `-pagination`, `-selection`, `-view-options`) and hooks (`use-data-table-keys`, `-virtualizer`), all files of one registry item. `data-table.tsx` re-exports the parts, so imports stay `@/components/tanstack/data-table`.

Chart keeps the rule across a library boundary. TanStack Charts paints its own tooltip, so `Chart` hands it `ChartTooltipContent`, which builds the tooltip from parts (`ChartTooltip`, `-Title`, `-Row`, `-Label`, `-Value`, `ChartIndicator`) the consumer can compose through `renderTooltipBody` instead. The legend is parts outside the chart (`ChartLegend`, `ChartLegendItem`, `ChartIndicator`), bound to it only by the app's state, so either can be replaced whole. A `ChartConfig` names and paints each series once, as shadcn's does, but as a plain value passed where it's read, not a context: `chartColor(config)` gives the definition its color scale, `Chart` and `ChartLegendContent` take it to label the tooltip and legend. The config, legend and `ChartIndicator` live in `chart-legend.tsx`, a second file of the `chart` item that imports nothing from TanStack Charts at runtime, and `chart.tsx` doesn't re-export them: a bundler keeps a module in one chunk, so an app that lazy-loads `Chart` keeps the library out of the chunk that renders the legend.

- **One part, one element.** Each part wraps a single element or Base UI part and is a named export (`Alert`, `AlertTitle`). No config-object props that hide structure; if it renders, it's a part. A part that announces (Copy Button's "Copied") renders its live region as a slot-less sibling, since inside the control its text would join the control's name and a slot would make it a group's last part.
- **A text input is three elements.** `Input` is an `InputGroup` box around `InputGroupInput`, a slot holding a bare `<input>`, after Interfere's. On a touch screen the input renders at 16px, so iOS doesn't zoom on focus, and scales by `inputVars.scale` back to the box's text size. It outgrows its slot in layout, and the slot keeps that from pushing the addons. `sx` styles the box; every other prop goes to the `<input>`.
- **Customizing a part, in this order.** Each kind of part takes one kind of customization:
  1. **Inline marks** (Shimmer, Code, Link, Swap Text) take their font and size from the text around them and have no size or color props. They set a color only when the color is what they mean (Link's `textPrimary`, Shimmer's sweep). To size one, put it in a `Text`: `<Text color="muted"><Shimmer>…</Shimmer></Text>`.
  2. **A part with its own look** (Button, Badge, Alert) takes `variant`, `size` and `color` where it has them.
  3. **Containers** take parts and children. Text inside is a `Text`; with no `size` or `weight` it takes its parent's, so it fits the part it sits in.
  4. **`render`** swaps the element. A part takes it when its element is a real choice: a title that may be a heading, a row that may be a link, a mark that may be another tag. A part that bundles another component (`DialogCloseButton`, `ToastAction`, `AlertDialogCancel`, `DropdownMenuInput`, `TraceCollapsibleTrigger`) omits it, since a caller's element would replace the bundled one and its styles; build from the underlying parts instead.
  5. **`sx`** for the rest, on the element that draws the part. An input's goes to its `InputGroup` box. A part whose surface sits in a shell (Sidebar's panel, Trace's collapsible content) puts it on the surface. Table's container is out of reach, as in shadcn.
- **Base UI and ui-sdk pass-throughs take `sx` too.** A Trigger, Close, Group or Portal renders an element, so it omits `className` and `style` and takes `sx`, and so does Collapsible's root, which renders a `div`. Other roots and providers render none and pass their props through. Given `render={<Button />}`, put `sx` on the Button. The Button applies its classes last, so the Trigger's would be dropped.
- **`variant` is how it's drawn, `color` is the color it means.** `variant` changes shape and emphasis (`primary`, `secondary`, `outline`, `ghost`, `link`, Card's `well`, Marker's `border`) and never names a color. `color` names a meaning, never a hue (Chart's `color` is a series paint, the one exception): `success`, `info`, `warning`, `danger`, and on text also `primary`, `secondary`, `muted`. Each part lists the colors it draws, and every variant takes them, so no pair is silently ignored. A part whose only look is its color (Text, Heading, Caption) has just `color`. `state` is lifecycle (Trace, Attachment, Prompt Input's submit). Avatar Badge's dot is `presence`. Toast keeps Base UI's `type` and its `error`, since `toast.promise` sets it.
- **Every value list is exported and mirrored.** Each prop's values are an `as const` list the type derives from (`textSizes`, `codeBlockColors`), and the part writes the value as a `data-*` attribute by hand. A part with `render` passes its attributes to `mergeProps` first, before the caller's props, so a caller or a wrapping trigger can write over them. The control scale below is for controls; type (`base`, heading levels) and containers (Card's `flush`, Dialog's `full`) keep their own.
- **Every part has a `data-slot`.** Even unstyled Base UI wrappers, so a parent can style around a child (`:has(> [data-slot="alert-action"])`) without a prop. A ui-sdk part sets its own and ignores one passed in, so a part built on it (`ModelPickerTrigger`) keeps ui-sdk's (`popover-trigger`). Button is the exception, since other parts render through it: it renders a passed slot over ui-sdk's `button`, so a part built on it (`sidebar-trigger`, `copy-button`) or a trigger rendered as it (`popover-trigger`, `dialog-trigger`) keeps its name, and a bare Button is `button`. Variants and sizes are mirrored as `data-variant`, `data-size`.
- **A part reused unchanged keeps its parent's slot.** `ApprovalHeader` is `CardHeader` re-exported, with `card-header`, because Card's selectors read those slots (`[data-slot='card'][data-size='sm']` sizes the title). Only a part that adds styles gets its own slot.
- **Convenience parts bundle the boilerplate.** `DialogContent` renders Portal, Backdrop and Popup, as in shadcn. The underlying parts stay exported for when it doesn't fit.
- **`sx` overrides, not `className`.** Parts omit `className` and `style` and take `sx?: Sx`, applied last in `stylex.props(...)` so the caller wins. `Sx` lives in `lib/constella/styles.ts`, which ships in `base`, so every item has it. It takes only tokens, as longhands, for color, space, radius, `boxShadow`, `fontSize`, `zIndex` and motion; other properties stay open. Past the tokens it takes `null` (unset), `0`, `auto`, `currentColor`, `inherit`, `transparent`, `ease` and `linear`; math (`calc`, `min`, `max`, `clamp`) with a space or size token in it; a radius token times a factor; a shadow built on a variable; and a motion list that starts with a token. Shorthands and pseudo-elements are rejected. A part passing its own styles into another part's `sx` meets the same type. The one wider prop is ScrollArea's `viewportSx`: a scroll fade sets custom properties and a `1ms` scroll-driven animation, which `Sx` can't express. `packages/ui/type-tests/sx.ts` holds what it rejects and its known gaps.
- **Variants are style keys.** `variant` and `size` index a `satisfies Record<Variant, StyleXStyles>` map, and the allowed values are one exported `as const` list (`buttonVariants`) the type derives from. No cva, no class strings.
- **The caller picks meaning, not the component.** Never derive a variant or color from the value (a full meter turning red); the same value means different things in different apps, so expose the prop and leave the choice to the caller.
- **Every control has the size scale.** `xs`, `sm`, `default`, `lg` (and `icon-xs`, `icon-sm`, `icon`, `icon-lg` where it has icon-only sizes), shadcn's names. Text fields skip `xs`: 24px is too short for typed text. The default is a real value, so `size="default"` can be passed, not only implied.
- **Styles for other elements are a function.** When an element must keep its own semantics (a link styled as a button), the component exports a style getter (`buttonStyles`) instead of rendering through `render`.
- **State comes from Base UI's and ui-sdk's data attributes** (`[data-open]`, `[data-disabled]`, `[data-starting-style]`), never mirrored into React state.
- **Groups talk to their children through variables.** A `ButtonGroup` sets the `joins` vars (`inline`, `block`, `either`) to `0`; a joinable child multiplies its corners and start edge by them, by whether it's the group's first or last part: `:nth-child(1 of [data-slot]:not([popover]))`, not `:first-child`, because Base UI drops focus guards and a portal placeholder beside an open popup's trigger, and ui-sdk renders an open popover's content in place beside it. Outside a group they stay `1`, so nothing changes. A part that must stay whole inside a group (an input group's addon) resets them to `1`.
- **A component's own variables are `defineVars` in `tokens.stylex.ts`** (`joins`, `avatarVars`). StyleX's types reject a raw `--custom-property` key, and `defineVars` only compiles in a `.stylex.ts` file.
- **Repeated style shapes are helpers.** StyleX evaluates arrow functions inside `stylex.create`, not function declarations, so those helpers are arrows with `func-style` disabled around them.

## Styling boundaries

Learned from Linear's move to StyleX ([Styling Linear for the future](https://linear.app/now/styling-linear-for-the-future-stylex)): the patterns hardest to keep correct at scale are the ones that style at a distance. Every rule here keeps a component's look readable from its own file.

- **A component owns its look.** What a part looks like is written in its file. A child may adapt to where it sits by declaring the condition itself (Spinner's `:is([data-slot='badge'] *)`); a parent may change its own layout by what it holds (`:has(> [data-slot='field-content'])`). A parent never styles a component or element it didn't render.
- **`sx` is the only way in.** No `className`, no `style`, no wrapping a component to restyle it. A part that takes `sx` passes it last, and a wrapper passes it through, never drops it.
- **`base.css` is the only escape hatch.** Global CSS only for what StyleX can't reach: third-party DOM, and children a component doesn't render (the outline badge's icons). Each rule there says why it can't be StyleX.
- **Longhands only.** StyleX resolves a shorthand against its longhands by property priority, not by order, so mixing them across styles that merge silently changes the winner. No multi-value shorthands either.
- **Structure from JS before structural selectors.** When a parent can know a child's position or state without it leaking, pass it as a prop or `data-*`, not `:first-child`/`:nth-child`. Group joins stay CSS: context passes through portals, so every popup opened from a group would join too.
- **Nothing pinned covers content that scrolls under it.** A sticky cover and the content under it are anti-aliased apart where they're clipped, so at a fractional scroll offset the content shows through its edge. Pinned parts sit beside the scroller instead: Code Block's line numbers and diff marks are absolutely placed against the content outside its `pre`, so they neither scroll nor clip. A mask that must spare them goes on that ancestor (`scrollFade.xEndAround`, on the scroller's named timeline).
- **Shared interaction states.** Every highlight is the same pair: the hover value behind `media.hover`, and the same value ungated on `:active` (its specificity beats the media block's `default`), so touch gets a press highlight and never a sticky hover. An open trigger's state (`[data-popup-open]` from Base UI, `[aria-haspopup][data-open]` from ui-sdk, whose collapsible triggers carry `data-open` too) repeats inside the media block, since StyleX layers that block above a bare condition. StyleX can't evaluate an imported function inside `stylex.create`, so the shared pairs ship from `styles.ts` as created styles, applied after a part's own (each replaces its whole property): `stateStyles` (`ghost`, `outline`, `secondary` fills, and `selectedFill`/`selectedFillLifted` for a pressed toggle) and `trackStyles` (Progress and Meter's bar, label and value). A pair only one component uses stays written out in its file.
- **In-place popups reset what they inherit.** ui-sdk renders popup content beside its trigger, in the top layer, so it inherits from wherever the trigger sits: a group's `joins`, an addon's color, weight, cursor and `user-select`, a table cell's `white-space`. `popoverStyles.popup` resets those on the content; a part that draws its own popup applies it.
- **Portals carry the theme.** The theme is a class on `<html>`, so a portaled popup inherits it. The one subtree theme, the color-roles demo panel, holds no popups. If a theme is ever set on a subtree, every portaled part must re-apply it, or its popups render in the page's theme.
- **Themes are tokens, never branches.** If themes are ever generated (a user's accent or contrast), they set the same `defineVars` tokens; components still read only tokens.

## Tokens

Components hold no design values. Every size, weight, color, layer, distance, blur, opacity, duration and curve comes from `packages/ui/src/lib/constella/tokens.stylex.ts`; a value a component needs that no token covers becomes a token first. Only structural values stay inline: `0`, `1`, `100%`, flex and position keywords, and `calc()` over tokens.

A group `Sx` reads (colors, space, sizes, radii, shadows, fontSizes, layers, durations, easings) is `as const`; without it its values widen to `string` and `sx` takes anything. A new token-bearing property joins the lists in `Sx`. `Sx` checks only what comes in through `sx`; a component's own `stylex.create` is held by lint and review.

Fixed tokens are constants, so JS reads the same values the styles do: a Web Animations call takes `durations` and `easings`, an icon takes `sizes` and `strokes` (by control size through `controlIconSize` in `styles.ts`), a popup takes `offsets`, a delay takes `Number.parseFloat(durations.fallbackDelay)`. CSS outside StyleX (view transitions in `base.css` and the site's theme switch) reads `motionVars`, `--duration-*` and `--ease-*` variables built from the same constants as `durations` and `easings`, so the two can't drift. Themeable tokens (`radii` but `full`, `sizes.control*`, `space` from `xs`, the drops in `shadows.default*`) are `var()` references to variables `base.css` defaults, so JS never reads them.

Layout lengths are rem, so they grow with the reader's browser font size along with the type scale: `space`, `sizes` and `strokes.track` multiply a local `spaceUnit` (`0.25rem`, Tailwind's `--spacing`), and the theme's `--radius`, control heights and spacing are written in rem. Lines, shadows, blurs, motion distances and `offsets` stay px. [space.md](design/space.md#units) has the reasons for each group. Base UI takes its offsets in px, so a distance that has to follow rem is a CSS `translate` (a submenu's alignment), not a prop.

## Theme

Switched by a `.dark` class on `<html>`: Radix's dark scales are scoped to that class, and it's what shadcn and next-themes already set, so a consumer's existing toggle works. The site follows the system until the visitor picks one.

Components never branch on the theme. Every color is a token valued by a Radix step, so the `.dark` class flips it. Not `light-dark()`: Lightning CSS lowers it to fallbacks that ignore the class, and the color comes out invalid.

Two files hold the system's values. `tokens.stylex.ts` is the system: roles as tokens, durations, easings, layers; a consumer doesn't touch it. `theme.stylex.ts` is theirs: one `defineVars` of what a theme sets, under literal `--` names (StyleX keeps a key that starts with `--`) so `base.css` can read them: the `--neutral-*` and `--accent-*` scales, each step pointing at a [Radix Colors](https://www.radix-ui.com/colors) scale by name, the roles valued by those steps (`--border`, `--fill`), the accent's roles, `--radius`, control heights, spacing, the depth's `--shadow-*` drops and the two fonts, `--font-sans` and `--font-mono`, named but not shipped. `base.css` sets `--font-sans` on the page; `reset.css` makes controls inherit it and sets `code`, `kbd`, `samp` and `pre` in `--font-mono`, as Tailwind's preflight does; Kbd and a chart value name the other. Our neutral scale isn't named `--gray-*` because a variable can't default to itself. Roles that differ between light and dark (muted text, raised surfaces) stay in `base.css`, since `defineVars` can't condition on the `.dark` class; Radix's own dark files switch on it, so a theme needs no dark values. Corners derive from one `--radius` there too, so they stay concentric at any value. Control heights and spacing come in presets, not a multiplier, so heights stay even; the builder writes each preset's px as rem at a 16px root. Themes are named after stars and set colors only (grays and a default accent); radius, sizing and depth are picked on top. Depth is `raised` or `flat`: the theme holds only the drops under controls and in-page surfaces, each a whole shadow so parts can list it after a ring or an inset fill, and flat sets them to `0 0 transparent`, since `none` is invalid in a list. A ring that draws an edge stays in `tokens.stylex.ts`, and `lg` and `xl` stay constants, since floating surfaces keep their shadow at any depth. Polaris is the `theme.stylex.ts` Constella installs. A consumer edits the file, or replaces it with the site's builder output; runtime-switchable themes are `stylex.createTheme(theme, …)` on `<html>`. No package and no generator: accents are Radix's named scales, hand-tuned in both appearances, and `@radix-ui/colors` already comes with `base`.

## Lint

`@constella/lint` turns the rules here and in `DESIGN.md` that drift into errors, so a person or an agent building on the system hears about it at once. It follows `@shadcn/lint`: one file per rule in `src/rules`, `plugin.ts` maps them, no preset; the consumer lists the rules.

| Rule | Catches |
| --- | --- |
| `constella/box-edge` | `borderSubtle` on a whole-box border color (`borderBlockColor`, `borderInlineColor`) |
| `constella/hover-media` | A `:hover` condition outside `[media.hover]`, so touch never sticks; reads keys built from the file's own top-level consts and templates, not imported ones |
| `constella/no-focus-style` | Any `outline*` in a component's styles |
| `constella/no-raw-colors` | A Radix step or hex in styles, not a `colors` token |
| `constella/no-shorthand` | A four-side shorthand (`margin`, `padding`, `inset`, `border`, `borderRadius`, `borderWidth/Color/Style`) in styles; it loses to any longhand merged in through `sx` |
| `constella/no-shorthand-mix` | A two-side shorthand (`marginBlock`, `borderInlineColor`) in a file that also sets one of its longhands; StyleX lets the longhand win whatever the order |
| `constella/sx-last` | `sx` passed to `stylex.props` or in an `sx` array anywhere but last |
| `constella/type-scale` | A raw font size, or a plain `fontSizes` step outside `typeStyles`; raw steps are for a size that changes by condition, paired with the same `lineHeights` |

The root `vite.config.ts` turns four of them off for `packages/ui/type-tests/**` only, since those fixtures hold raw values on purpose.

A rule earns its place when a correction comes up twice. Add one there before writing the same note again.

CI (`.github/workflows/ci.yml`) runs `check` and `build` on each push to `main` and each PR, so a broken rule shows up even when no one ran it locally.

## UI SDK watch

[UI SDK](https://ui-sdk.dev) (`vercel-labs/ui`, Apache-2.0) is a headless behavior library: `@ui-sdk/core` holds keyboard, focus, selection, dismissal, popups, drag and drop and their ARIA, with adapters for React 19+, Vue, Svelte, Solid and Web Components. It ships importable parts for the components Base UI covers, plus Color Picker, Image Cropper, Date and Time Input, Token Input, Tree, Timeline and Rating. We migrate from Base UI to it once it's ready. Until then, build on Base UI and log each check here.

### Agent bridge

The reason to move. Official docs: [Built for Agents](https://ui-sdk.dev/docs/agents) and its [Reference](https://ui-sdk.dev/docs/agents/connect-an-agent/reference). `createAgent()` from `@ui-sdk/react/agent` returns a bridge every UI SDK component registers with, so an agent drives the UI through component APIs instead of screenshots and clicks. Fits Constella's AI components: an assistant built from Chat and Prompt Input can operate the rest of the app.

| Piece | Does |
| --- | --- |
| `snapshot()` | Every component with a short `ref`, kind, accessible label, state and allowed actions; a closed Select lists its `items` |
| `query()` | Finds components by text, or lists the choices inside one |
| `act({ steps })` | Runs steps in order by `ref` or label; returns each step's `changes` and every field's `values`. A failed step stops the call with no rollback; `ok: true` doesn't mean each change was accepted |
| `allow` on `createAgent` | Sees each step first; `false` or a promise refuses or asks. Optional, and without it every supported action runs. `timeout` defaults to 5 minutes |
| `subscribe(listener)` | Every change with `previous`, `reason` and `source`, for an "edited by your assistant" log |
| `createHistory`, `stageChanges` | Undo by source and staged, revertable changes. Experimental |
| `data-agent-confirm`, `-hidden`, `-secret` | Needs a person; hidden from the agent; value redacted (password, card and OTP fields by default) |
| `details.source` in change callbacks | `agent` beside `keyboard`, `mouse`, `programmatic` and others; `details.cancel()` refuses. `withSource` keeps it across an `await` |
| `definePrimitive({ agent: { actions } })` | Exposes a custom component's methods; without it the bridge guesses `setX`, `open`, `toggle`, `clear` |
| `registerTools(agent, { allow })` | Publishes the three tools on WebMCP's `document.modelContext`, with a second, stricter `allow` for the browser's agent |

The bridge sees only UI SDK and `definePrimitive` components, and the docs give no way to register other elements, so a page that mixes libraries gives the agent a partial view. That argues for migrating whole, not component by component. It runs in the browser only; `agentTools` gives the schemas, and the app runs its own model loop. The docs conflict on whether `query` opens a popup to read its choices, so assume it may, and `allow` runs after a component is found, so a popup can open before a refusal.

### Same model as Base UI

- Parts per component (`ToastRegion`, `Toast`, `ToastTitle`, `ToastDescription`, `ToastAction`, `ToastClose`), imported from `@ui-sdk/react/<component>`.
- `render` on every part, as an element or a function of props and state. No `asChild`, as in Base UI.
- `data-slot`, state attributes (`data-open`, `data-side`, `data-disabled`) and `data-starting-style`/`data-ending-style` for exits.
- Popup placement props: `side`, `align`, `sideOffset`, `alignOffset`, `collisionPadding`, `anchor`.

### Port notes

Status and PRs are tracked in [ui-sdk-migration.md](ui-sdk-migration.md).

From the 0.1.0-beta.1 docs in `node_modules/@ui-sdk/react/docs` and the `ui-sdk` skill, then the Popover spike (2026-11-14), which proved the rows it names.

| Topic | Note |
| --- | --- |
| Layers | ui-sdk injects a small runtime stylesheet in a top-level `ui-sdk` layer on first mount. Undeclared, it lands last and beats StyleX's layers. As ui-sdk's docs say, the app's global stylesheet declares `@layer ui-sdk;` first: the site's `styles.css`, and the install docs and registry `docs` tell consumers to. Not in `base.css`: a layer declared before its import, like Tailwind's, would sit below `ui-sdk`. Built order: `ui-sdk, reset, base, priority1…11` |
| `web.css` | Not imported. It centers dialogs and places the toast region by `data-side`/`data-align`, so our styles take that over. The browser's `[popover]` box (inset, margin, padding, border, overflow, background) is reset by ui-sdk's runtime layer, not `web.css`, for `popover-content` at least; it also sets `color: inherit`, so the content sets its own color. Proved by Popover |
| `data-slot` | ui-sdk owns the slot; parts built on it carry ui-sdk's names, and only Button yields to a passed one. Names change: `dropdown-menu-*` to `menu-*`, `dialog-popup` to `dialog-content`, `toast-viewport` to `toast-region`, `radio-group-item` to `radio`, `input-group-control` to `input` or `textarea`. Popover's keep theirs; Model Picker's trigger and content became `popover-trigger` and `popover-content`. Every part built on Separator (Button Group's, Item's, Sidebar's) carries `separator`, and the selectors that told them apart read it inside their group. Nested parts resolve to the innermost: a raw ui-sdk Button inside `PopoverTrigger` reads `button`, so ours renders a passed slot back over it ([Composition](#composition)). Core 0.1.0-beta.1 reads no button or trigger slot; recheck on each bump |
| Open state | Triggers carry `data-open`/`data-closed`, not Base UI's `data-popup-open`, and no `data-pressed`. Collapsible triggers carry `data-open` too, so an open-popup style reads `:where([aria-haspopup])[data-open]`, at the specificity of Base UI's `[data-popup-open]`. Proved by Popover |
| In-place popups | Content renders next to its trigger, in the top layer: an `overflow: hidden` ancestor doesn't clip it. It counted in the group joins' `:nth-child(1 of [data-slot])` and squared an open trigger's end corners, so the joins skip `[popover]`. It inherits from where it sits, so the content resets that ([Styling boundaries](#styling-boundaries)). DOM events bubble through it, as React's already did through a portal. Positions land on fractional pixels, where Base UI rounded. Proved by Popover |
| `--available-height` | ui-sdk registers it and `--available-width` page-wide without inheritance as soon as a popover mounts, before it opens, and the registration outlives client-side navigation. Base UI sets them on the positioner and our popups read them a level down, so Select, Dropdown Menu, Hover Card and Prompt Input's command lost their max size. Their positioners copy them into `popupVars`. A ui-sdk popup reads them on its content, where they're set; an inner scroller copies them first. Proved by Popover |
| Mixed Field | ui-sdk's Field binds a Base UI control it finds only after mount, so a Base UI control in it calls `useFieldControl` from `@ui-sdk/react/field` to carry the label's `for`, description, name, `disabled` and `invalid` from the server's HTML on (Select, Slider). Slider hands the description to each thumb's input, as Base UI's Field did. ui-sdk writes the label's `for`, so `FieldLabel` takes no `htmlFor`. Proved by Field |
| Field sets | `FieldLegend` is a native `<legend>`, outside the set's flex flow. A `FieldDescription` right inside a `FieldSet` describes the set. The legend names the `fieldset`, not a radio group in it, so that group takes `aria-labelledby`. Proved by Field |
| Progress | Same slots and state attributes (`data-indeterminate`, `data-progressing`, `data-complete`) as Base UI, so styles didn't change. The value formats in English on the server and first render, then in the page's `lang`. Custom text goes through `format`, which both `ProgressValue` and `aria-valuetext` read. `ProgressValue` stays `aria-hidden`, since ui-sdk 0.1.0-beta.1 doesn't hide it. Proved by Progress |
| Scroll Area | Our `ScrollArea` renders children straight into `ScrollAreaViewport`, with no `ScrollAreaContent`: ui-sdk watches the viewport and its direct children, and its docs say a horizontal scrollbar makes the content part grow as wide as it needs, which would undo Code Block's full-width lines. Bars show under `[data-visible]` with the default `type="hover"`; `scrollHideDelay` is 0 (the exported `scrollHideDelay`, which Code Block's hand-built root also passes), so leaving hides the bar at once. The delay also covers the end of a scroll, so a bar shown by scrolling fades about 150ms after the scroll stops, where Base UI held it about 600ms. ui-sdk sets the root's `position`, and the bars' `position`, `touch-action`, `user-select` and insets inline; the insets size the long axis and stop each bar short of the corner, so our bar's long axis is `auto` (a StyleX `null` under a condition would leave the `default` 10px in place). With no Scrollbar part ui-sdk keeps the native bars, so `scrollbar="none"` adds `scrollbar-width: none` to the viewport. A viewport that holds a link or control isn't a tab stop. ui-sdk counts overflow in whole pixels (`scrollWidth` against `clientWidth`, 1px tolerance) while Chromium makes any sub-pixel overflow a keyboard-focusable scroller, so a viewport that overflows by under a pixel takes a Tab stop ui-sdk gives no `tabindex`. A Tab sweep over 86 docs pages found it on 12 of 946 page-widths at a 16px root and 8 of 258 at 17px, all Code Blocks and tables; Base UI had none. A `test.fails` in `scroll-area.test.tsx` pins it until ui-sdk gives such a viewport `tabindex="-1"`. Code Block's root and Table's container carry `scroll-area`, so the focus ring reads `[data-slot="code-block"] > [data-slot="scroll-area"]`. Thumbs follow the computed direction, so Code Block drops `DirectionProvider` and keeps `dir="ltr"`. A thumb's length is the viewport's share of its scroll width; Base UI's ran short by the gutter on a numbered Code Block. Every scroll area shows in the agent `snapshot()` as a `scroll-area` with no actions, unnamed unless its root has an `aria-label`. Proved by Scroll Area |
| Gaps | Menu documents no search input part (ours ships `dropdown-menu-input`); no anchored Toast |
| RTL | No `DirectionProvider`; it reads the page's direction, also when `dir` changes after load. Proved by Popover |
| SSR | No provider. Prerendered popover pages hydrate with no warnings; trigger ids are `ui-sdk-<useId>-trigger`. Runtime CSS arrives after hydration, and closed `keepMounted` content relies on the `[hidden]` rule `reset.css` already has. Agent bridge and `observe` start in client code only. `data-review-loc` likely mismatches hydration the way StyleX's `data-style-src` did |
| Motion | Popover's open, close and reduced-motion frames match Base UI's frame for frame. No `data-instant` outside Tooltip; `useSkipMotion` reads `details.source` and commits with `flushSync`, since ui-sdk reads the content's transitions right after `onOpenChange` |
| Agent | A popover's `snapshot()` entry is named by its trigger while closed and by its title while open, and lists the buttons inside. In jsdom a `fireEvent` change reports `source: "programmatic"`, so keyboard paths need a browser |
| Mixed libraries | Not tested: a Base UI popup (Select, Menu, Tooltip) opened from inside a ui-sdk popover should render under it, since the popover sits in the top layer, above any z-index. No demo does this today |
| Testing | `@ui-sdk/core/testing`: `checkPattern` for 15 ARIA patterns, `mount` with `keys`/`click`/`drag`, `checkServer`, `checkDirection`. Vitest and jsdom with `__UI_SDK_STRICT__` and the stubs in the skill's `testing.md` |
| Extras to use | `createConfirm()` (awaitable Alert Dialog), `useShortcut` and the `shortcuts` registry, `useAsyncOptions`, `presentation="sheet"`, async Close `action`, `debug` prop on roots |

Spike order: Popover (layers, popover reset, slots, motion, hydration), then Toast (region placement, stack variables), then Menu with a submenu and an agent-bridge test.

## Gotchas

- **Equal-specificity StyleX conditions emit in StyleX's own order.** Exclude one with `:not()` and check the built CSS.
- **Key order never makes a StyleX condition win; specificity does.** An override (like `:is([data-instant] *)`) loses to a more specific condition on the same property, so pair it with each one (``[`${iconOnly}${fromKeyboard}`]``) and check every state it covers.
- **Lightning CSS lowers `:dir(rtl)` to a `:lang()` list.** Write `:is([dir='rtl'], [dir='rtl'] *)` instead.
- **Base UI places slider thumbs and popups by its own direction, not `dir`.** An RTL app also wraps it in Base UI's `DirectionProvider`; a physical `translateX` in our styles flips under the `dir` selector.
- **Base UI Root `children` can be a render function.** Wrap providers outside Root, not around its children.
- **Chat demos stream through `fakeText()` from `@tanstack/ai/testing`.** `@tanstack/ai` is a site-only dependency; `chat()` runs the fake in the browser behind the client's `stream()` connection. Keep `@tanstack/ai` at `@tanstack/ai-client`'s version so only one copy installs.
